FAQ

How does login work? (Google OAuth setup)

This admin panel uses Google OAuth. Only accounts on an allow-listed domain can sign in.

Server env vars:

GOOGLE_CLIENT_ID=xxxxx.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=xxxxx
SESSION_SECRET=<random 32+ char string>
ADMIN_ALLOWED_DOMAINS=ramosjames.com    # comma-separated for multiple
PUBLIC_URL=https://your-host.com         # used to build the OAuth redirect URI

Google Cloud Console setup:

  • Create an OAuth 2.0 Client ID (Web application) at console.cloud.google.com → APIs & Services → Credentials.
  • Add https://your-host.com/admin/auth/callback as an Authorized redirect URI (replace your-host.com with the actual host).
  • Copy the Client ID and Client Secret into the env vars above.

Sessions are signed HMAC-SHA256 cookies with a 12-hour lifetime. If SESSION_SECRET is not set, the server generates a random one at startup and everyone is logged out on restart.

How do I set a firm's credentials (Quo key, Slack token, webhooks)?

Two ways — you can mix and match per field:

  • In this UI (recommended for new firms): enter them in the Credentials section of the Add/Edit form. With Postgres configured they're stored in the database (encrypted if SECRET_ENCRYPTION_KEY is set) and survive redeploys. This makes onboarding fully self-service.
  • As env vars: per-firm and named FIRM_<UPPERCASE_ID>_<VAR>. Env vars always take precedence over UI-stored values, so a field set in the environment shows as "from env" and is read-only in the form.

The full set of credential fields (for firm id smithlaw, the env-var names would be):

FIRM_SMITHLAW_QUO_API_KEY
FIRM_SMITHLAW_SLACK_BOT_TOKEN
FIRM_SMITHLAW_SLACK_TEXT_MESSAGES_WEBHOOK_URL
FIRM_SMITHLAW_SLACK_MISSED_CALLS_WEBHOOK_URL
FIRM_SMITHLAW_SLACK_HUMAN_CALLS_WEBHOOK_URL
FIRM_SMITHLAW_SLACK_SONA_CALLS_WEBHOOK_URL
FIRM_SMITHLAW_SLACK_LEAD_CALLS_WEBHOOK_URL
FIRM_SMITHLAW_SLACK_LEGAL_ASSISTANT_WEBHOOK_URL
FIRM_SMITHLAW_SLACK_LEAD_CALLS_CHANNEL_ID
FIRM_SMITHLAW_SLACK_LEGAL_ASSISTANT_CHANNEL_ID

ANTHROPIC_API_KEY is shared across all firms (used only for lead classification) and stays an env var — there's no per-firm version.

Is it safe to store credentials in the database?

The admin panel is gated behind Google OAuth restricted to your domain, and the API never returns stored secret values (the UI only shows "saved / not set / from env"). For defense in depth, set SECRET_ENCRYPTION_KEY to any strong passphrase — credentials are then AES-256-GCM encrypted before they're written to Postgres, so a database dump alone can't reveal them. The key itself lives only in the environment, never in the database. Without it, credentials are stored as plaintext in the DB (still behind the database's own access controls).

What webhook URLs do I give Quo?

In Quo's webhook settings, point each event to the URL matching the firm's ID:

Messages:     https://<your-host>/webhooks/quo/<firmId>/messages
Calls:        https://<your-host>/webhooks/quo/<firmId>/calls
Call summary: https://<your-host>/webhooks/quo/<firmId>/call-summary

Each registered firm's exact URLs are shown in the firm card above once loaded.

How does Intake Extraction work?

When enabled, every qualified-lead call summary is parsed by Claude into a structured intake record (client, accident, injuries, insurance, vehicle, etc.) and written as one row to your intake table, with the Quo call link saved alongside it. Then it posts 📝 Intake loaded for [Name] to the notification channel (default #lead-calls).

  • Trigger: qualified leads only — spam/vendor/existing-client calls are skipped.
  • Where it writes: the same case database (CASE_DB_URL). The DB role needs INSERT on the intake table — e.g. GRANT INSERT ON public.intakes TO your_role;
  • Dedup: rows are keyed by call_id with ON CONFLICT DO NOTHING, so a call is never recorded (or announced) twice.
  • Fields: only what the caller actually says is filled in; everything else is left null for staff to complete.
  • Shape: every intake-form field is its own flat column (63 of them — referral, accident, client, property damage, employment, other driver, insurance, injury, notes), so the table is directly readable and editable by other apps. The raw extraction is also archived in a data JSONB column for debugging.

Base table:

create table public.intakes (
  id            uuid primary key default gen_random_uuid(),
  call_id       text unique,
  name          text,
  phone         text,
  quo_link      text,
  transcript    text,
  data          jsonb,
  created_at    timestamptz default now()
);

Then run the flat-column migration (MIGRATION.sql in the repo) to add all the intake fields, backfill any existing JSONB rows into them, and add name/phone lookup indexes. It's safe to re-run.

Editing from another app: read/write public.intakes keyed by call_id. The router only ever fills empty fields — it never overwrites a value that's already set, so anything staff type is safe from later follow-up calls. Connect server-side with the service_role key (RLS is on; the table holds client PII).

It's best-effort and runs after normal routing, so an extraction hiccup never affects the Slack call posts.

How do follow-up calls/texts get captured? (72h window)

When an intake is created, a follow-up window opens on that caller's number (default 72h, configurable). During the window, every call, text, voicemail, and Sona call on that number is:

  • logged as a row in the interactions table (linked to the intake by intake_call_id, deduped by the Quo message/call id), and
  • if it has any text (text body, call transcript, voicemail transcription), run through the extractor and merged into the intake — filling any fields that were still empty (existing values are never overwritten; lists are unioned).

You get a brief 📝 Intake updated — filled N fields Slack note whenever a follow-up adds something. Windows survive redeploys (rehydrated from recent intakes on startup).

It also looks backwards. Right after the intake is created, the router queries Quo history for messages/calls with that same number from the same look-back window (e.g. a text they sent an hour before the qualifying call), logs them as interactions, and merges their details in too. Items already captured live are skipped via the source_id dedup, so nothing is double-counted.

Create the interactions table:

create table public.intake_interactions (
  id             uuid primary key default gen_random_uuid(),
  intake_call_id text,
  phone          text,
  type           text,          -- text | call | sona_call | missed_call | voicemail
  direction      text,          -- inbound | outbound
  source_id      text unique,   -- Quo message/call id (dedup)
  content        text,
  transcript     text,
  quo_link       text,
  data           jsonb,
  occurred_at    timestamptz default now()
);
grant insert, select on public.intake_interactions to your_role;  -- if not the owner

Pull a full lead later by joining on intake_call_id:

select i.name, i.phone, x.type, x.direction, x.content, x.occurred_at
from public.intakes i
left join public.intake_interactions x on x.intake_call_id = i.call_id
where i.call_id = '...'
order by x.occurred_at;
How does Case Status (open/closed) work?

Quo only knows contacts, not whether a case is open or closed — that lives in your case-management database. Point the router at it (e.g. a Supabase Postgres) and it learns which cases are archived, so a call from a former client isn't buried in a dead case channel.

Setup:

  • Put the database connection string in the Case DB connection string credential (for Supabase, use the connection pooler URI). It's stored encrypted like other secrets.
  • Set the Case status query to a read-only SELECT returning case_number and status, e.g. SELECT case_number, status FROM public.cases. The case_number must match the number embedded in your Quo contact names.
  • List which status values mean closed (default archived).

The router syncs the table every ~30 minutes into memory (no per-call queries). When an event comes in for a closed case, it's posted to the case channel flagged ⚠️ CLOSED CASE — former client and also sent to #legalassistant-phone (intake), since a former client is often calling about a new matter — and it becomes eligible for lead classification again. Open cases and firms without this configured behave exactly as before.

Tip: expose a dedicated view (e.g. SELECT id AS case_number, status FROM public.cases) so you can refactor your real schema without touching the router.

How does "Only route events for the phone lines above" work?

By default the router posts every call and text the firm's Quo account sends — because one Quo account maps to one firm. If a firm's Quo account has several numbers but you only want some of them mirrored to Slack, turn on this toggle and list only the numbers you want.

With it on, an event is posted only if its from or to matches one of the listed phone lines; events for the account's other numbers are dropped (you'll see a "Skipped — neither … is a configured phone line" line in the logs). Matching is done on the last 10 digits, so a missing +1 country code won't break it — but list numbers in full +1XXXXXXXXXX form to be safe. With the toggle off, phone lines are only used for labeling and inbound/outbound detection.

Where do the Slack bot token and webhook URLs come from?
  • Bot token: create a Slack app in the firm's workspace, add scopes (chat:write, channels:read, groups:read, channels:history, groups:history, channels:join, users:read), install to workspace, then copy the "Bot User OAuth Token" (starts with xoxb-).
  • Incoming webhook URLs: in the same app, add "Incoming Webhooks" and create one per channel (missed-calls, sona-calls, human-calls, lead-calls, legalassistant-phone, text-messages).
  • Channel IDs: in Slack, right-click the channel → View channel details → scroll to bottom, or open the channel in browser and grab the ID from the URL.
The channel-topic tagging isn't working for a firm. Why?

The bot reads @mentions live from each case-channel's topic (via conversations.info) every time it posts. If mentions aren't showing up:

  • Confirm the bot is in the case channel (it auto-joins on first post — check it wasn't kicked).
  • Confirm the channel topic contains actual Slack mentions like <@U12345>, not just @Name text.
  • Confirm the bot has channels:read/groups:read scope.
What does the fallback call-check do?

Quo occasionally never sends call.completed or /call-summary events, which would otherwise leave the call silent in Slack. On the ringing event, the router schedules a check 185s later. Before acting, it queries GET /v1/calls/{callId} to get the real status, then routes based on what actually happened (missed / menu-hangup / answered by Sona / answered by human). Each firm has its own set of pending timers.

How is data isolated between firms?

Each firm has its own contacts cache, users cache, Slack channel cache, call cache, pending-call-check timers, and resolved-call set. A rate-limit or bug affecting one firm's cache load does not affect another. Secrets (Quo API key, Slack bot token, webhook URLs) come from env vars named FIRM_<ID>_* and are never shared. The only shared piece is ANTHROPIC_API_KEY.

Where are firms stored? (Postgres vs firms.json)

There are two sources, loaded in this order at startup:

  • firms.json (committed to git) — holds the default firm (ramosjames). This never changes and always loads first, so the original firm keeps working regardless of the database.
  • Postgres — holds firms added through this admin UI. Loaded after firms.json. Requires DATABASE_URL to be set.

When you add a firm here and DATABASE_URL is set, it's written to the firms table and survives redeploys automatically. If DATABASE_URL is not set, the firm is written to firms.json on disk instead — which is ephemeral on most hosts, so you'd need to commit it to git (the success screen gives you the blob).

How do I set up the Postgres database?

Provision a Postgres instance (Fly Postgres, Render, Neon, Supabase, etc.) and set its connection string as an env var:

DATABASE_URL=postgres://user:pass@host:5432/dbname
DATABASE_SSL=                 # leave unset for managed DBs (SSL on by default)
                              # set DATABASE_SSL=disable for a local/no-SSL DB

The router creates the firms table automatically on first boot (CREATE TABLE IF NOT EXISTS) — no migration step needed. Secrets (Quo API key, Slack tokens, webhook URLs) are never stored in the database; they always come from FIRM_<ID>_* env vars.

How do I edit or remove a firm?

Each firm card has Edit and Delete buttons.

  • Edit loads the firm into the form above; change the name, practice area, phone lines, or tag users and click Save Changes. The firm ID can't be changed. Edits apply immediately and persist to wherever the firm lives (Postgres or firms.json).
  • Delete removes the firm from the router immediately and from its store (Postgres row or firms.json entry). It does not remove the firm's FIRM_<ID>_* env vars — clean those up in the deployment separately.
  • The default firm (ramosjames) can't be deleted from the UI — it's the anchor firm in firms.json. You can Edit it, but since it lives in firms.json, the change is written to disk and must be committed to git to survive a redeploy.
Legacy Quo webhook URLs (without /<firmId>/) — still supported?

Yes. The old routes /webhooks/quo/{messages,calls,call-summary} route to DEFAULT_FIRM_ID (default: ramosjames). You can migrate URL by URL at your own pace, or leave the default firm on the legacy URLs and only use per-firm URLs for new firms.
